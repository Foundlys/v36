# Explicit templates to internal drafts

The existing owned template catalog now prepares an internal Communication draft through native controls or the same selected-source ZERO controls. It never sends mail. Messages remains a count of retained messages, with the existing unavailable/incomplete-count rules intact.

Only literal `{{field_name}}` placeholders are supported, using lowercase ASCII letters, digits and underscores, at most 32 unique fields. Values are explicit strings, at most 2,048 characters each and 16,000 serialized characters together. There are no expressions, executable markup, inferred CRM values or provider lookups. Unknown/reserved/malformed fields, unsafe subject controls, invalid recipients and oversized results are refused. Substitution runs once; `$&`, markup and placeholder-looking text inside a supplied value stay literal. Missing values yield `ready_to_create: false` with null body/title/fingerprint, rather than an apparently complete draft.

`POST /api/communication/templates/:id/draft-preview` accepts variables and optional To/Cc. Creation at `POST .../:id/drafts` additionally requires the exact source revision/hash, actor/tenant/input-bound preview fingerprint, explicit confirmation/reason and idempotency key. Both require current Communication and drafts write authority plus current template access. Creation, immutable draft history, reference-only audit and action receipt persist atomically. An exact retry under current source conditions returns the same draft after encrypted restart; conflicting keys, changed templates or revoked rights do not create another draft.

The draft retains the applied template ID, revision, content hash and values hash. Later catalog edits do not rewrite the saved draft or invalidate an otherwise unchanged exact-content approval. Current template access still governs the derived draft, revisions, comments, attachments, editing, sharing, review and owned export. Deletion or reassignment that withdraws source access withdraws derived access. The private reference cannot be forged through generic draft input. Approved SMTP acceptance retains the original template reference with the recorded outbound message; acceptance still does not prove delivery. Existing independent reviewer, purpose preferences, exact account/content binding and separate send confirmation remain required.

ZERO exposes template preview and internal draft creation through the same service. It preserves the selected template, explicit action and replay key, and retains only references/hashes rather than template text or values in conversation results/audit. Native and ZERO forms show inert text, invalidate previews on every value/recipient edit (including A-B-A), suppress repeated pending saves and discard detached results.

`communication-templates-test.js` covers substitution, bounds, rollback, source access, replay, retained versions, exact review and isolated accepted transport. `communication-templates-api-test.js` uses actual enrolled sessions, encrypted restart, native/ZERO handoff and template/permission/owner changes while the server awaits a request body. `communication-templates-client-test.js` exercises production handlers with a DOM fixture. These are not live provider, actual browser, keyboard, viewport or comparative product acceptance. Broader template lifecycle, provider workflows, delivery evidence and remaining masterbuild capability/acceptance gaps stay in scope.
