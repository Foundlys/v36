# Retained delivery report inspection

Phase 24 continues from Marketing checkpoint `36bce2d3daf54562886be01035f81fd2d76b81ce`, tree `5fb1a418cfb617cde53bbc5c33336fc627cdbb69`. Existing provider submission, recovery, inbox, approval and permission contracts are preserved.

Native `GET /api/communication/messages/:id/delivery-report` and typed ZERO `DELIVERY_REPORT` inspect one currently authorized retained IMAP source. The original byte hash, mailbox/UID binding and current provider-draft exclusion must agree. The supported subset is an outer multipart/report with delivery-status, two or three parts, a bounded message/delivery-status block, and optional returned text/rfc822-headers or message/rfc822. Unsupported encodings, duplicate/contradictory fields, ambiguous recipients and malformed or oversized sources remain unavailable. Recipient addresses use rfc822 syntax; international/non-rfc822 formats are not claimed.

Each recipient retains its reported failed, delayed, delivered, relayed or expanded action and enhanced status, original/final address and diagnostic text. Matching requires an exact returned original Message-ID, one accessible outbound message, current source-draft access and an accepted submission whose immutable MIME hash agrees. Recipients are compared to the original sent To/Cc headers with case-preserved local parts. Missing recipients and mismatches remain explicit; a report for one recipient cannot imply full-recipient coverage. Missing original headers or ambiguous current accessible submissions do not produce a match. Correlation is scoped to accessible retained submissions, not global mailbox completeness.

All output remains an untrusted report. SMTP acceptance, UNKNOWN attempts, send/retry decisions, recipient preferences, delivery_verified and business records are unchanged. No source lookup contacts a provider. Authenticated mailbox receipt does not authenticate the report's sender or prove its claims. [RFC 3464, sections 2–4](https://www.rfc-editor.org/rfc/rfc3464.html) defines the report format and explains the possibility of forgery. The implementation preserves this distinction instead of treating a syntactically valid report as independent delivery proof.

The current inbox has explicit native and ZERO inspection controls, literal diagnostics, source-revision checks, denied-source clearing and detached-response refusal. Tests cover all five actions, malformed/duplicate/corrupt sources, partial recipient scope, exact immutable MIME correlation, private/withdrawn source access, UNKNOWN preservation, native/ZERO current replay, encrypted HTTP restart and source-free ZERO history. UI evidence is synthetic DOM, not actual browser acceptance. The isolated fixture uses an OS-assigned port and never accesses a real mail account.

Authentic provider delivery/bounce receipts, unknown attempts without durable observations, cross-host retirement/fencing, live provider/account behavior and real browser/competitive acceptance remain BLOCKED_EXTERNAL / UNVERIFIED. This increment closes the bounded code-controlled inspection gap; it does not close all Communication or Phase 24 acceptance, authorize production, or complete Phases 25–31.
