# Order and CRM invoice creation in both priority demos

The production Finance page now has a separate expandable order-invoicing panel. It reads native legal entities, owned Sales orders and readable CRM customers in bounded pages of fifty. Orders and customers have explicit server-side search and independent previous/next controls. Authored invoice numbers and dates survive source paging. Every source change clears the prior preparation and confirmation. Order identifiers, customer identifiers, saved order totals, source coverage and the selected customer's saved billing address remain visible as literal source values.

An order's free customer reference does not silently become a CRM identity. The user explicitly selects the actual readable contact. The preview resolves current supplier, CRM address, order revision and contact revision through the existing native `COMMERCE_INVOICE_CREATE` contract. It shows supplier and customer details, dates, each native-calculated invoice line and the exact total. Prices and tax come from the saved order; a later catalog price change does not rewrite that order. The client never supplies edited source prices or fabricated billing identities. Cancelled, returned or already linked orders remain visible and receive explicit native blockers where applicable.

The panel uses the existing native Finance API or structured ZERO, chosen through the existing page transport selector. Creation links a single draft to the order atomically. It does not post a journal or record a payment. Current Finance/Sales/CRM capabilities and tool permissions determine whether the panel mounts; a Finance-only accountant does not acquire Sales or CRM authority. A current capability/tool loss removes the unavailable view even when it contains a dirty preparation.

Exact confirmation metadata is retained under the current owner in encrypted server storage before execution. A lost committed response survives restart. Recovery displays the original draft separately from the current invoice and verifies the original/current order and CRM links. A request that never ran is retired and its supported invoice fields/visible selections are restored for a new explicit preparation. No abandoned request is automatically executed. Detaching during retention prevents a late execution; detaching during source search prevents old-view rehydration. Post-acknowledgement read failures remain known saved results, with no financial retry. Initial concurrent reads settle before the final failure message so a later source response cannot replace that outcome.

All twenty-four new message keys have entries in the eight current locales. Language changes preserve the exact selected IDs, authored values, confirmation and request count. Source strings resembling HTML render as literal text. The existing responsive field and button styles are reused; this is not a substitute for actual browser, focus, screen-reader or installed-device review.
