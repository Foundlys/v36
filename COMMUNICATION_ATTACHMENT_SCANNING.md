# Local attachment scanning

Communication retains UTF-8 `.txt` attachments up to 64 KiB using its existing text validation. These legacy text attachments remain labelled `NOT_PERFORMED` for malware scanning.

PDF, PNG and JPEG uploads up to 256 KiB require file-signature checks and an explicit successful local ClamAV scan before being attached. Signature checks identify supported file envelopes; they do not prove document integrity or safety. Current draft/source/write access, revision and any active editor grant are checked before, during and after scanning. Scan alerts, unavailable engines, old databases, timeouts and malformed responses never produce a successful attachment. Source bytes are passed through stdin, with no shell, remote submission, inherited application credentials or user-controlled command arguments. Each scan uses a private temporary directory, removed after the child exits.

The runtime invokes `/usr/bin/clamscan` by default. Deployment configuration can select an absolute executable using `FOUNDLY_CLAMSCAN_PATH` and an absolute signature database file/directory using `FOUNDLY_CLAMSCAN_DATABASE`. Neither option is writable through the product API. An operator must supply and maintain a legitimate ClamAV installation and official signature database. This run has not installed or changed production dependencies. The available scratch runtime had no `clamscan` executable; child-process fixtures verify integration, not actual engine detection or database acceptance.

The invocation requires official signatures no older than two days, enables alerts for encrypted files, macros and exceeded limits, and bounds time, extracted size, recursion, output and concurrent processes. An exit code of zero is accepted only with the exact successful stdin result and a stable, current database version before and after the scan. An exit code of one means the scanner raised an alert, which may be a heuristic or limit rather than a proven infection. Other outcomes remain unavailable.

The encrypted attachment retains immutable bytes, their SHA-256, the engine/database identity, observation time and a scan receipt hash. `NO_THREAT_DETECTED` describes that observation and is explicitly not a safety guarantee. Review and submission require a scan observed within 24 hours and a database published within 48 hours. Re-adding an expired binary attachment performs a new scan and retains the earlier file/receipt for historical references; remove the old reference from the current draft. Historical read/export survives scan expiration. No background deletion or silent rescan changes an approved snapshot.

Up to ten current attachments and 640 KiB of current combined bytes are supported. Binary retention is bounded to twenty files per draft, two thousand per tenant and 16 MiB per tenant, alongside existing text retention. Capacity errors retain history. Files download as hash-checked attachments; binary bytes use `application/octet-stream` and are never rendered inline. SMTP review covers the immutable file hashes and scanner metadata.
