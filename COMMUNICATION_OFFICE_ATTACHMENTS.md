# Larger files and bounded Office attachments — Phase 24 continuation

This extends the existing Communication attachment/review/submission path. It does not complete the masterbuild, prove a real scanner or provider, or authorize production changes.

Scanned PDF, PNG, JPEG, DOCX, XLSX and PPTX files may be at most 3 MiB each. Current attachments may total 6 MiB, with the existing ten-file limit and retained tenant quotas preserved. The 9 MiB wire bound accommodates those bytes plus MIME base64 folding and headers. The existing API body limit is unchanged: one maximum-sized encoded file fits below it. Public metadata and native upload controls use the same limits. Source bytes remain private, encrypted and inert on download.

Office packages receive bounded in-memory ZIP inspection before the existing local ClamAV process. The implementation accepts stored/deflated entries and matching data descriptors; validates local/central names, flags, sizes, CRC32 and complete compressed-stream consumption; and limits entry count and aggregate expanded bytes. It refuses encryption, multipart/ZIP64, traversal, alternate Unicode paths, duplicate case-folded paths, symlinks, overlapping or hidden records, unexpected extras, known macro/ActiveX/embedded-object parts, dangerous XML declarations and missing package parts. It never extracts paths to disk, renders XML, follows relationships or executes document content. Positive structural results use a bounded digest cache containing only numeric metadata, avoiding repeated inflation during current-authority reference checks.

The package check is not a document renderer or a safety guarantee. Content always remains untrusted. Required local malware scanning still enforces official recent databases, strict successful exit/output, no inherited application secrets, current actor/configuration throughout subprocess execution, time/output/resource limits and refusal of encrypted/macro/limit alerts. V2 uses a 4 MiB scanner file bound and 32 MiB expanded scan bound; the Office structural limit is stricter at 24 MiB and 500 entries. Legacy V1 scan receipts remain readable for their original PDF/PNG/JPEG types and at most 256 KiB. They cannot authorize a newly supported Office file or a larger payload. No historical file or receipt was rewritten.

Tests use independent Python-standard-library ZIP fixtures, including streaming data descriptors, deliberate malformed packages, actual isolated scanner child processes, real native HTTP sessions and encrypted restart. A two-file 6 MiB service scenario verifies exact approved originals inside more than 8 MiB of MIME, current designated approval, isolated provider acceptance, retained action replay without resending and unchanged draft/message semantics. Actual Google/SMTP acceptance, real malware detection, Office rendering, browser/keyboard/viewport behavior and high-load production acceptance are not claimed.

Other formats, larger provider limits, richer attachment workflows, remaining inbox/receipt requirements and all unresolved capability ledgers remain in scope. Current quotas are explicit bounds, not proof of full competitive parity.

Primary format references checked 2026-09-11: [PKWARE ZIP specification 6.3.10](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT) and [Node zlib documentation](https://nodejs.org/api/zlib.html). These describe format and decompression behavior; they are not account, document-rendering or malware evidence.
